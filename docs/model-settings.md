# Model and reasoning settings

The Model & reasoning section in Setup & connections saves independently of credentials. Its controls work for ChatGPT login and API-key connections. The default remains `gpt-6-sol` with reasoning `off`; an existing saved model is preserved. The single `generation` settings record persists model/reasoning atomically in app.sqlite. Old `model` settings are read until the user saves new preferences. UI loads actual saved preferences rather than defaulting its dropdown every time.

Only text chat models with the installed `openai-responses` transport are offered. Realtime/audio/specialized-only entries and legacy GPT-4/GPT-4 Turbo are excluded. Thinking levels come from Pi's actual `getSupportedThinkingLevels` model map, including null exclusions. Invalid combinations are rejected on save, send and resume. Changing to a model that does not support the chosen reasoning level requires an explicit new choice. No request silently substitutes another model or reasoning level.

The list is an **offline compatibility catalog**, not proof of account access. Official [SIWC models documentation](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) describes an authenticated GET /v1/models (`models[]`, visibility=list, slug/display_name) for current account choices. Pebble does not fetch that account list automatically in this milestone or claim it has checked entitlement. A selected setup is confirmed only after a successful completed assistant response in the current owner session. Changing settings or credentials resets confirmation; no verification badge is carried across restart. A future user-triggered account-catalog refresh can narrow the offline list without making inference calls.

Both initial Harness configuration and each new request/resume receive the saved model and thinkingLevel. Pi forwards non-off levels as streamSimple.reasoning and maps them to Responses reasoning.effort. For the default GPT-6 Sol, off maps to none. Settings are rejected while a response is running. Saving preferences makes no model request and never changes or reads back credentials.

Verification: bun test runtime/model-settings.test.ts runtime/http.test.ts covers catalog filtering, model-specific reasoning, HTTP hydration, real Harness execution with synthetic model transport, persistence/reopen, credential-method switches and exact SIWC/BYOK request serialization. Synthetic 403 responses verify no model fallback. verification/model-settings.mjs uses the separate port7351 build with all APIs mocked and external requests blocked; it checks hydration, save without an API key, incompatible reasoning, reload/provider switching, pending/error states and responsive widths.

Activation requires one coordinated restart of the durable owner. Until then the UI gracefully reports that settings become available after restart and keeps existing connections active. The running owner has deliberately not been restarted; reconnecting Discord and model credentials after that restart must be coordinated with the user.
